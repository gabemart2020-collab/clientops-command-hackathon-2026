# 0007: Trusted Agent Runtime invocation boundary

Status: Accepted architecture decisions: B1 offline signed invocation contract and B2 DynamoDB OWNER/REPLAY store selection. B2 implementation and all later runtime/cloud work remain separately gated.
Date: 2026-10-15; DynamoDB decision recorded 2026-10-16.
Authority: User authorization for B0 documentation, B1 offline implementation, and the later DynamoDB architecture selection dated 2026-10-16. This ADR records the decisions and does not grant implementation/provisioning authority.
Architecture baseline: `phase/5.2.3-b0-trusted-runtime-architecture@49426c6777053877acc9c53f8fdfa78dc080add5`.
Related: ADR 0006; `docs/PHASE5_CONTRACTS.md`; `docs/PHASE5_2_RUNBOOK.md`.

## Problem and threat model

The existing Agent Runtime can validate a strict V1 request and apply an offline caller policy, but its HTTP handler receives only a JSON body. The caller-policy context is an injected string, not an AWS-verified identity. Its ownership implementation is process memory. `main.ts` composes an intentionally unbound AgentCore MCP invoker. Therefore, matching UUIDs, a certification allowlist, SigV4 at ingress, or a valid JSON request alone does not establish a cryptographic relationship among the caller, the requested actor/organization, and the logical retry.

Threat actors include arbitrary network clients, compromised or misconfigured trusted callers, replaying callers, concurrent runtime instances, malicious content in user/tool data, compromised application credentials, and overprivileged runtime roles. The security goal is to reject forged identity and retries, preserve proposal idempotency, confine the agent to grounded proposals, and fail closed when authentication, storage, configuration, catalog, or database dependencies cannot be verified.

## Accepted prior decisions (unchanged)

- ADR 0006 separates IAM/SigV4 machine authentication from human identity and preserves Phase 4 authority separation.
- Browser-direct AgentCore invocation is prohibited. The model receives exactly five READ/ANALYZE business tools; `system.get_status` is diagnostic only.
- PostgreSQL remains authoritative business/action/audit state. The proposer may register only grounded `task.create` proposals through `PENDING_APPROVAL` and its designated audit events.
- The Agent Runtime does not approve, deny, execute, or mutate tasks. Memory, model text, transport session state, and request claims do not grant authority.
- Existing Phase 5.1 MCP reader and Phase 5.2.2 proposer database roles retain their frozen privileges. This ADR authorizes no privilege expansion.
- Phase 5.2.3-A is offline-only and non-deployable. Gate A merged as PR #10.

## Accepted decisions

### B1-approved offline decisions (2026-10-15)

The user explicitly approved the following bounded design for offline contracts and tests: JWS Compact serialization; ES256 (P-256/SHA-256); RFC 8785 JSON Canonicalization Scheme; exact protected header `typ=clientops-invocation+jws`, `alg=ES256`, and allowlisted `kid`; explicit public-key-to-caller authorization; a dedicated trusted application caller; synthetic server-owned staging organization/actor; signature-bound `NEW` and `RETRY`; a maximum envelope lifetime of 120 seconds; and maximum accepted clock skew of 30 seconds. The signed request fingerprint covers the complete strict V1 request including identity, request/session IDs, message, and optional-field semantics. The offline verifier accepts canonical JCS request bytes so duplicate JSON names and noncanonical encodings cannot be hidden by ordinary JSON parsing. These are approved B1 architectural decisions, not external AWS requirements.

B1's offline signer/verifier and ownership decision contract do not bind HTTP ingress or the runtime handler. They do not establish AWS IAM identity, consume replay IDs atomically, prevent verbatim replay, provide durable ownership/idempotency, or authorize agent execution. B2 must implement and verify durable atomic ownership/replay and recovery before any invocation path can be enabled. No production ownership store is implemented in B1.

The later user-approved decision dated 2026-10-16 selects DynamoDB as the dedicated durable invocation OWNER/REPLAY store. This is an architectural selection only, not approval to implement B2, provision AWS resources, grant IAM access, configure KMS, activate enforcement, deploy, or invoke remotely. The B1 chronology above remains intact: B1 itself selected no store and authorized only offline contract implementation. KMS key creation/use and private-key custody remain future-gate work.

The accepted architecture places a trusted application caller in front of AgentCore, uses a signed invocation envelope verified by the runtime, and uses a dedicated durable request-ownership store. IAM authorization answers “may this AWS principal invoke this runtime?” The envelope answers “which authorized logical request and certification identity did the trusted application authorize?” Neither replaces the other. The runtime must not infer or trust an AWS principal passed in arbitrary headers or body fields. AgentCore principal forwarding to arbitrary application code is not assumed; a later live gate must verify the actual service behavior and SDK metadata available.

### Signed envelope

Versioned signed claims are `envelopeVersion`, `callerId`, `audience` (exact runtime identity/environment), `intent` (`NEW` or `RETRY`), `organizationId`, `actorId`, `requestId`, `sessionId`, canonical payload fingerprint, `issuedAt`, `expiresAt`, and unique `replayId`; the `kid` is only in the exact JWS protected header, not a claim. The signature covers the canonical encoding of every claim. Neither a browser nor untrusted JSON may select authoritative intent or identity. The trusted caller derives intent from its own logical invocation state and signs it. The payload fingerprint covers the strict V1 request after schema validation and deterministic canonicalization, including optional-field semantics. Envelope claims are accepted only after signature and policy validation. A future runtime binding must derive the trusted caller from a configured caller/key allowlist, then check audience, certification identity, intent, time window, replay ID, and payload fingerprint before ownership lookup or agent work.

`NEW` means the trusted caller generated a fresh request ID. Ownership may be created only by atomic insert-if-absent/first-write-wins (`getOrCreate`); if that ID already has an owner, reject the NEW invocation as a conflict, even if fields happen to match. `RETRY` requires an existing request owned by that same caller. It uses lookup/verification only (`find`), never creates ownership. Unknown but syntactically valid RETRY IDs are rejected with no ownership or replay-marker insertion. Check owner existence and all immutable fields before atomically consuming the RETRY replay ID. Cross-caller reuse, changed payload, changed session, or conflicting ownership fails closed. This preserves Gate A's `getOrCreate` versus `find` distinction.

The B1-approved format is asymmetric JWS Compact ES256 with an explicitly configured public-key allowlist. Offline tests may generate ephemeral keys; no private key is committed. Private signing material must never enter the runtime. Key IDs are explicit; verifier configuration may provide a bounded overlap of current and retiring public keys; retired/unknown/revoked keys fail closed. B1 does not choose a production key source or custody system. KMS-backed signing, key creation, distribution, revocation operations, and emergency rotation procedures remain future-gate work. Signature verification and RFC 8785 canonicalization use maintained libraries and fixed test vectors.

The ownership store must durably and atomically consume each `replayId` and detect duplicates across concurrent processes. Verbatim replay of the same signed envelope is rejected, including concurrent submissions. Retain replay-ID duplicate records for at least as long as the envelope can be accepted, including allowed clock skew; concrete duration is unresolved. A crash, timeout, ambiguous write result, or store outage during replay-ID consumption fails closed; the invocation must not proceed to agent or proposer work until a later fresh envelope is safely verified. There is no in-memory-only replay protection. The chosen store/API must make replay-ID consumption atomic with the corresponding NEW ownership creation or RETRY owner verification step, or use an equivalently safe single-record representation. On conflict, distinguish duplicate replay ID from request ownership conflict without permitting either to proceed.

An authorized RETRY is a freshly signed envelope with `intent=RETRY`, fresh `replayId`, and the original immutable logical request identity: request ID, caller, organization/actor, session, and canonical payload fingerprint. It cannot claim an unknown request UUID, switch caller, change payload, or replace the original session. Expired envelope replay is rejected before agent work. Ownership must never be reassigned when a TTL expires, cleanup is delayed, or ordinary request metadata is deleted: retain an immutable ownership record or permanent non-reassignment tombstone/key reservation. The B1-approved maximum lifetime is 120 seconds and maximum accepted clock skew is 30 seconds. Concrete replay retention/TTL and schema remain later decisions; expiry may clean auxiliary data only if it cannot permit request-ID reuse.

### Durable ownership store

Accepted architectural decision (2026-10-16): DynamoDB is the dedicated durable OWNER/REPLAY store for invocation coordination. It is isolated from PostgreSQL business, proposal, approval, task, and audit authority. Logical ownership identity is scoped by runtime/environment and logical `requestId`. Immutable ownership attributes include caller, certification organization and actor, stable request and session IDs, and canonical payload fingerprint. `NEW` uses atomic conditional first-write-wins ownership creation; existing ownership cannot be reassigned. `RETRY` is find-only for ownership; unknown RETRY creates neither ownership nor replay marker. RETRY requires strongly consistent owner lookup or an equivalently safe transactional verification; stale reads cannot authorize invocation. Signed replay IDs are consumed durably and atomically with the relevant ownership decision. Verbatim and concurrent replay attempts fail closed. Verify owner identity and all immutable request fields before retry replay consumption. Bound conflict retries, timeouts, and total latency; no stale-read or in-memory fallback may authorize an invocation. Storage outages, uncertain writes, conflicts, timeouts, and ambiguous outcomes fail closed. TTL is cleanup only; expiration or deletion must never permit reuse of an old logical `requestId`. The initial architecture targets one approved staging region and assumes no cross-region coordination. No raw user prompts, credentials, signatures, tool outputs, or provider errors are persisted. PostgreSQL remains the authoritative business system of record; no cross-store transaction or exactly-once execution guarantee is claimed.

The selection does not settle a concrete table/key/index schema, retention duration, capacity, backup, encryption or operational settings, IAM role/policy/resource ARN, staging resource names, KMS custody/deployment, crash recovery implementation, runtime integration, execution lease/fencing, or retry response caching versus agent re-execution. These remain future design and certification gates. No DynamoDB resource is asserted to exist.

This store coordinates invocation ownership and replay prevention only; it is not business truth, proposal state, approval state, or an exactly-once transaction with PostgreSQL. A crash after ownership creation but before proposal registration leaves a safely retryable owned request. A crash after proposal commit is recovered through the existing proposal correlation/idempotency behavior using the same `requestId`. A crash or ambiguous response during either step must not mint a new request ID. Cross-store atomicity with PostgreSQL is not claimed; later integration evidence must establish recovery and no duplicate proposal/audit effects.

PostgreSQL alternative: place ownership in a separately controlled table and claim it transactionally. This could reduce stores, but the existing proposer role is intentionally narrow, PostgreSQL proposal transactions do not span model work, and the table/schema/grants would require database change authority and privilege review. Extending proposer privileges would couple invocation ownership to business/proposal authority and weaken the frozen boundary. DynamoDB was selected to isolate caller retry coordination from PostgreSQL authority and avoid that privilege expansion. It adds a service, IAM, cost, retention, and operational dependency; its implementation and controls remain future gates.

### Transport session distinction

Logical request ownership identity is scoped by runtime/environment + logical `requestId`; caller and canonical payload fingerprint are immutable ownership attributes. `sessionId` is stable metadata of that logical request. AgentCore transport/session IDs are opaque transport correlation only and must never establish actor, tenant, authorization, idempotency, or retry ownership. Transport retries cannot silently become new logical requests.

## Alternatives considered

1. Trust SigV4 alone and read caller identity from an assumed AgentCore header/context. Rejected as an implementation assumption: application forwarding semantics are unverified and arbitrary headers are forgeable unless the platform authenticates and strips/controls them.
2. Trust body certification identity and UUID syntax. Rejected: caller ownership is unproven; Gate A policy itself documents this limitation.
3. Static shared bearer secret. Rejected: weak caller attribution and rotation/replay handling; conflicts with ADR 0006 prohibition on long-lived static service bearer tokens.
4. Signed envelope without durable store. Rejected: valid envelopes can be replayed concurrently and across restarts; cannot enforce first-write-wins ownership.
5. PostgreSQL ownership table. Viable alternative, but requires schema/grant changes and couples retry authority to proposer data privileges.
6. DynamoDB conditional ownership store. Selected on 2026-10-16 for isolation and conditional ownership/replay coordination. SDK/API verification, IAM review, provisioning, and AWS certification remain future gates.

## Trust boundaries and rationale

Browser/user content is untrusted. Gate B does not implement or claim a production human authentication path. The staging certification organization/actor is synthetic and server-controlled; identity-provider integration remains a separate future gate. The trusted application applies this synthetic certification identity, creates logical request identifiers, canonicalizes the payload, and signs the envelope. AWS IAM/SigV4 separately gates machine invocation. Runtime verifies the envelope and claims durable ownership before invoking Strands. Strands sees only five business READ/ANALYZE tools through the concrete AgentCore data-plane adapter. Evidence capture, grounding, and proposer registration remain inside the runtime trust unit. The proposer secret is fetched only by the runtime role through exact Secrets Manager access; database target checks and `clientops_agent_proposer` preflight remain mandatory. MCP runtime retains its distinct `clientops_mcp_reader` role.

The asymmetric envelope provides application-level request integrity and attribution even if the platform does not expose caller context. It does not protect a compromised signer, establish production human identity, or make agent output trustworthy. Durable ownership provides concurrency-safe retry identity but does not make DynamoDB atomic with PostgreSQL. Least privilege and database enforcement continue to contain compromise.

## Unresolved decisions requiring explicit approval

- Trusted caller deployment/location, caller ID provisioning, and how it obtains AWS invocation authorization.
- Public-key distribution, production key custody, KMS signing authorization, and operational overlap/rotation/revocation process.
- Concrete audience identifier and environment binding; replay retention/TTL policy.
- Concrete DynamoDB table/key/index schema; exact replay retention duration; capacity, backups, encryption, and operational configuration; and implementation recovery details.
- Execution lease and fencing policy; retry response behavior and exact response idempotency contract (cache a prior response, re-execute the agent, or another approved policy).
- IAM role, policies, resource ARN, access grants, concrete staging resource names, and KMS key custody/deployment approach.
- AgentCore ingress/runtime integration and cross-region behavior beyond the initial single approved staging region.
- How to handle an ambiguous proposal registration commit and ensure proposal/audit event deduplication without changing existing database contracts.
- Concrete AWS SDK and AgentCore data-plane request/response behavior, caller-principal forwarding semantics, limits, error shapes, and retry semantics.
- Secret ARN/configuration ownership and required workload role boundaries.

## Verification requirements

Before any later gate, offline tests must cover canonicalization vectors, valid/invalid signatures, key rotation and unknown keys, audience/time/fingerprint mismatch, forged caller claims, NEW insert-if-absent versus RETRY lookup-only behavior, unknown RETRY with zero insertion, changed/cross-caller/session conflicts, atomic concurrent ownership writes, durable atomic replay-ID consumption, verbatim concurrent replay rejection, restart-safe reads, store timeout/outage/ambiguous-write behavior, bounded conflict handling, injected crash points, exact catalog enforcement, sanitized errors, and proposal/audit duplicate behavior. Offline tests establish application logic against fakes/local deterministic stores only; they do not establish AWS SigV4 enforcement, AgentCore metadata forwarding, KMS policy/key behavior, DynamoDB conditional consistency/TTL, IAM effective permissions, Secrets Manager access, network boundaries, or PostgreSQL staging grants.

Gate sequencing is fixed by the project: Gate B is offline trusted runtime integration; Gate C covers image build, provenance, and scanning; Gate D is separately authorized AWS provisioning; Gate E is Agent Runtime deployment; Gate F is remote certification without live proposal writes. Phase 5.2.4 separately authorizes, when explicitly approved, live proposal, retry, and tenant-isolation certification. These scopes are not interchangeable or implied by completion of an earlier gate. Actual signed invocation, effective IAM/trust policy, KMS/key lifecycle, durable service-store concurrency/restart behavior, concrete AgentCore catalog, proposer secret retrieval, and database role checks belong only to the relevant separately authorized later gates.

## Deployment limitations

The overall trusted-runtime integration architecture records the accepted B1 offline envelope decisions and B2 DynamoDB OWNER/REPLAY store selection. Neither decision asserts that the integrated runtime has been implemented or deployed. B1 authorized offline contract implementation only; the 2026-10-16 B2 decision authorizes documentation only. No production credentials, committed private-key fixtures, AWS resources, database schema, runtime bindings, signed invocation enforcement, or deployment authority are created or implied. B2 implementation, image creation, provisioning, deployment, and live certification require separate authorization. Gates C, D, E, and F retain their distinct scopes. Phase 5.2.4 live proposal/retry/tenant-isolation certification requires its own explicit approval. Gate B does not implement or claim production human authentication; staging certification identity remains server-controlled and synthetic. Identity-provider integration is a separate future gate. No AgentCore Memory, expanded model authority, new action types, database changes, or live proposal writes are authorized here.
